# 串聯系統：指標與演算法方法說明

本文件說明目前程式實際採用的計算方式、參數來源與限制。所有數值應以現行程式碼及可重現腳本為準，不將展示資料的結果解讀為企業正式導入後的成效。

## 1. 證據來源與參數定位

專案需求來自 6 段訪談與 24 份跨部門協作問卷。訪談涵蓋營運管理層、投資研究部、資產管理部與業務開發部；問卷用於確認交接、知識留存與跨部門協作等痛點。

五維健康度的方向與優先順序參考管理層訪談；`28% / 24% / 20% / 16% / 12%` 的精確數值則是團隊為了保持排序、總和為 100%，且避免單一面向支配總分所設定的設計參數。它們不是由 5 位管理層排序或統計估計所得，也不代表經過企業長期實證校準。

所有指標定位如下：

- 用於辨識異常、安排會議與資源配置的管理提示。
- 不直接作為員工績效、獎懲、分潤或責任歸屬依據。
- 展示版採示範資料；正式導入後仍需以實際資料重新校準。

## 2. 組織健康度

五個面向皆轉換為 0 至 100 分，分數越高代表當下狀況越健康：

| 面向 | 權重 |
|---|---:|
| 決策及時 | 28% |
| 交接流暢 | 24% |
| 部門協作 | 20% |
| 卡點健康 | 16% |
| 負載均衡 | 12% |

總分公式：

```text
overall = 決策及時 × 0.28
        + 交接流暢 × 0.24
        + 部門協作 × 0.20
        + 卡點健康 × 0.16
        + 負載均衡 × 0.12
```

主要扣分邏輯：

- 決策及時：已完成決策平均處理時間超過 14 天後，每多 1 天扣 3 分；每筆逾期決策再扣 10 分。
- 交接流暢：由完成率形成基礎分，每筆待簽收且逾時至少 24 小時的交接扣 8 分。
- 卡點健康：每件 3σ 卡點扣 18 分、每件 2σ 卡點扣 10 分；平均百分位超過 50 後，每增加 1 百分位再扣 0.6 分。
- 負載均衡：綜合 Gini、2σ/3σ 人數、最高負載占比與最大 z-score，而非只看單一排名。
- 部門協作：以部門間提及與交接的雙向程度衡量，避免把單向大量傳遞誤認為良好協作。

實作位置：`src/lib/orgHealth.ts`。

## 3. 員工負載

負載分數由最近四週的週報與交接訊號組成：

```text
loadScore = timeWeightedCases + blockerLoad + mentionsWeighted + handoffLoad
```

### 3.1 時間衰減

最近四週依序使用：

```text
[1.0, 0.7, 0.4, 0.15]
```

四週以前的資料不納入目前負載分數，避免很久以前的工作持續影響當期判讀。

### 3.2 訊號權重

- 一般案件列：`1.0 × 時間權重`
- 含協助或跨部門語意的案件列：`1.5 × 時間權重`
- 含卡住、延誤、缺漏或逾期語意的案件列：`2.0 × 時間權重`
- 自己週報中的卡點：每項 `2.5 × 時間權重`
- 被其他週報提及：每次 `1.5 × 時間權重`
- 待簽收且自己是接收者的交接：每件 `4.0 × 時間權重`
- 其他交接參與：每件 `1.5 × 時間權重`

### 3.3 異常判定

系統先計算全體員工負載的平均數、標準差、百分位與 z-score：

```text
z = (個人 loadScore - 全體平均 loadScore) / 標準差
```

- `z >= 3`：critical，顯示為 overload。
- `2 <= z < 3`：warning，顯示為 high。
- 未達異常門檻且 `loadScore >= 6`：normal。
- `1 <= loadScore < 6`：low。
- `loadScore < 1`：idle。

若樣本少於 10 人，z-score 容易低估單一人員承擔大部分負載的情況，因此加入最高分占總負載比例：占比至少 80% 視為 critical；至少 60% 視為 warning。

實作位置：`src/lib/algorithms.ts` 的 `analyzeEmployeeLoad()`。

## 4. 卡點風險

卡點的 `currentDays` 是從案件建立日至觀察日的停留天數。比較池依序採用：

1. 同類別已解決卡點及歷史案件。
2. 同類樣本至少 5 筆時使用同類池。
3. 不足 5 筆時退回全部歷史資料，避免小樣本產生不穩定門檻。

系統計算 P75、P90、P95、平均數、標準差、百分位與 z-score：

- 達到 P75：P75 關注。
- `z >= 2`：2σ 紅標示警。
- `z >= 3`：3σ 立即處理。
- 完全沒有歷史資料時，才使用 14 天與 21 天的 SLA 備援提醒。

因此這裡衡量的是「相較同類案件是否異常久」，不是用單一固定天數判斷所有案件。

實作位置：`src/lib/algorithms.ts` 的 `analyzeBlockerRecord()`。

## 5. 歷史案件搜尋

搜尋採 BM25F、中文 1/2/3-gram、原文子字串加分與 PMI 共現擴展。

BM25 參數：

```text
K1 = 1.5
B  = 0.75
```

欄位權重：

| 欄位 | 權重 |
|---|---:|
| 標題 title | 5.0 |
| 標籤 tags | 4.0 |
| 摘要 summary | 2.0 |
| 結果 outcome | 1.5 |
| 負責人 owner | 1.0 |
| 詳細內容 detail | 1.0 |

PMI 以「同一歷史案件內共同出現」作為共現事件。候選詞至少出現在 2 份文件、不得出現在超過 80% 文件中，且 `PMI >= 1` 才可加入；每個詞最多保留 8 個擴展詞。擴展權重限制在 0.18 至 0.45，避免關聯詞蓋過使用者原始查詢。

實作位置：`src/lib/historySearch.ts`。

## 6. 敏感度分析

`scripts/sensitivity_analysis.ts` 會對員工負載權重進行 500 次隨機擾動。2026-06-11 以目前 Seed 資料重新執行的結果如下：

| 權重擾動 | Top-3 名單穩定 | Top-5 名單穩定 | Spearman rho |
|---:|---:|---:|---:|
| ±10% | 100.0% | 99.9% | 0.997 |
| ±20% | 100.0% | 98.4% | 0.994 |
| ±30% | 100.0% | 97.0% | 0.989 |
| ±50% | 99.3% | 93.6% | 0.974 |

執行方式：

```bash
npx tsx scripts/sensitivity_analysis.ts
```

這項結果只表示目前示範資料下的排名對合理權重變動不敏感，不等於參數已由真實企業資料證明為最佳值。

## 7. 可重現驗證

```bash
npm run validate:params
npx tsx scripts/sensitivity_analysis.ts
```

驗證腳本用於確認公式、Seed 結果與文件描述一致。正式導入後應重新蒐集實際處理時間、交接紀錄與使用回饋，再調整權重及門檻。

## 8. 已知限制

- 目前尚未完成長期企業試用，因此不能宣稱固定節省多少小時或一定提前多少天發現問題。
- 問卷用於支持痛點存在，並未直接估計演算法權重。
- 五維權重及文字訊號係數屬於可審查的初始設計值，不是統計上的最適參數。
- 小樣本的百分位、標準差及 PMI 關聯仍可能波動，需搭配案件脈絡與管理判斷。
- 系統指標是討論起點，不應被單獨用來評價個人。
